# Dutch local dictionary

Dutch Reader now has two independent evidence channels in the same inspector:
local English-Wiktionary lexical evidence and generated meaning in the authentic
sentence. **Dictionary evidence != contextual meaning.** Local results do not wait
for or call an LLM. Russian contextual meaning remains generated by the existing
service; there is no FreeDict integration.

## Architecture and behavior

`reader/dutch.py` is a read-only service over an independently built SQLite file.
It does not mutate Reader Storage. The existing owner-authenticated endpoint
`POST /api/reader/{document_id}/lexical` accepts `mode: "dictionary"` and returns
`{"dictionary": {surface, normalized_surface, available, candidates, is_ambiguous}}`.
The mode is omitted or `"contextual"` for existing generated meaning. Both use the
same server-authoritative sentence/code-point-span validation. No client paths are
accepted. `target_language` remains `ru`/`en`; dictionary glosses are always English.

The capability registry declares `local_dictionary: "dutch"` for Dutch. Chinese
segmentation, pinyin, dictionary, Hanly and Mosaic keep their existing behavior.
Vocabulary saves retain surface/expression, contextual meaning, canonical sentence,
identity, span and timing. No migration/enrichment or Review scheduling change is made.
Review has no dependency on this dictionary.

The frontend starts local and contextual requests independently. Local data stays
visible during contextual Loading/Error/Retry and language switching. A 5-second
local transport deadline and 20-second contextual transport deadline prevent stuck
UI requests; the existing backend contextual deadline remains 45 seconds. An empty
successful contextual response is treated as retryable failure. Native expression
saving also uses the bounded contextual request and can save without a meaning.

When local lookup is unavailable/misses, the inspector explains this and continues
contextual lookup, speech and saving. Failed contextual lookup retains dictionary
information, speech and saving. No local entry is invented for missing compounds.
No guessed POS, article, plural, stemming, suffix rules or compound splitting exists.

## Evidence and presentation

Each lexical source record stays a separate candidate, including same-lemma/POS
records. Each sense retains its gloss list, labels and noun article/gender evidence.
Noun sense tags map neuter → het; masculine/feminine/common-gender → de. Generic
`common` is not gender. Missing evidence stays empty/null in presentation. Adjective,
verb or diminutive-form gender does not become root-noun gender.

Explicit forms are retained with their feature sets. Base plural excludes diminutive
plural; singular diminutives are secondary disclosure content. Multiple plurals stay
attested alternatives without frequency claims. A lexicalized diminutive retains its
own entry. Reference-only glosses are not lexical definitions. Form lookup follows
explicit lemma forms and `form_of`/`alt_of` references with matching POS, a visited set
and at most eight edges. Broken references/cycles cannot recurse indefinitely.

Candidate ordering is deterministic presentation only:

1. Exact spelling/case direct lexical evidence.
2. Ordinary candidates before a proper-name collision with different case.
3. Direct lexical records before indirect forms/references within those groups.
4. Stable case/normalized lemma/POS/source-record ID tie-breaks.

There is no `best_candidate` and no contextual disambiguation. Multiple records are
marked as multiple analyses; two appear initially, with access to the rest. Two senses
appear initially per record, with additional senses and singular diminutives disclosed.
Source sense order and historical/usage labels are preserved; no global historical
filter is applied. Articles shared across an entry's senses can appear by its lemma;
conflicting articles remain beside their respective senses and are explicitly marked
as sense-dependent, including when there is only one source-record candidate. Separate `mens` records
stay separate human/person vs derogatory/informal woman interpretations.

## Schema contract (version 1, builder 1)

- `entries`: source-record ID, original lemma, normalized lemma, POS, optional original
  source title (used for source links).
- `senses`, `glosses`: entry/ordinal and sense/ordinal/text, preserving grouping/order.
- `labels`, `sense_labels`: interned sense grammatical/usage labels, linked to senses.
- `surfaces`: original spelling and normalized lookup key, interned once.
- `features`: interned sorted feature sets separated by U+001F; no JSON blobs.
- `forms`: entry/surface/feature links, unique by that triple.
- `relations`: entry/normalized target/kind/feature links for explicit references.
- `metadata`: source identity, attribution/license, snapshot/checksums/revisions,
  builder/schema version, input kind/checksum, transformation and record counts.

Normalized keys reuse Reader's NFC/casefold/whitespace normalization. Apostrophes
and hyphens are preserved; straight/curly apostrophes are not guessed equivalents.
The artifact has foreign keys, uniqueness constraints and indexes `entries_key`,
`senses_entry`, `surfaces_key`, `forms_surface` plus primary/unique indexes. Runtime
opens `mode=ro`, sets `query_only`, validates required table columns, indexes,
source/schema/builder/language/input metadata and `quick_check`. Missing, corrupt,
incompatible or subsequently unreadable files return explicit unavailable state
and log a reason without leaking paths/provider details. Dictionary lookup never
scans the whole dictionary or holds it all in Python memory.

## Authoritative source and reproducible build

The source is the **raw** English-edition Wiktextract gzip, not the deprecated Dutch
postprocessed download. See [provenance gate](dutch-local-dictionary-raw-source.md).

- URL: https://kaikki.org/dictionary/raw-wiktextract-data.jsonl.gz
- Dump: enwiktionary 2026-09-02; extraction: 2026-10-03.
- Gzip: 2981058381 bytes; SHA-256
  `3dac8a09e57827bef493e2e6b552fe917bf3b1fc55dee05c4e4a3702aff5dbdb`.
- Dutch-only raw subset: 222550596 bytes, 146492 records; SHA-256
  `e63cb76e7cac43b8fa03d886bb0cda388f5ec8354e9f9c4854c2f46a7b4d9ff8`.
- Wiktextract `1a05e46f9efbccda6a2b2f8e21b30a9c0c46513a`;
  Wikitextprocessor `e3d6d4edb77618f4d6680edc66e3f774bea59820`.

From an already pinned Dutch-only raw subset:

```sh
python -m tools.build_dutch_dictionary \
  --source /path/to/raw-dutch.jsonl --output /path/to/dutch.sqlite3
```

Or directly from the pinned complete raw gzip (without a 25.6 GB intermediate):

```sh
python -m tools.build_dutch_dictionary --source-kind compressed \
  --source /path/to/raw-wiktextract-data.jsonl.gz --output /path/to/dutch.sqlite3
```

Both stream records and filter `lang_code=nl`. Parsing never downloads anything.
Input checksum is verified before building; a moving upstream URL cannot silently
replace the pin. Malformed records/build failures do not publish partial artifacts.
Output is published atomically, no-clobber by default (`--overwrite` is explicit),
with integrity/foreign-key checks and world-readable permissions for non-root Docker.
Metadata has no build timestamps, enabling deterministic bytes. Two local subset
builds produced the same SHA-256.

## Artifact/deployment decision

**Recommend B: a separately versioned release/download artifact**, accompanied by
`dictionary/LICENSE-DUTCH.txt` and `dictionary/dutch-artifact.json`. No generated
SQLite or raw source is committed. Publish/install is not performed by this task.

Why: 44 MiB is reasonable as an asset, but repeated Git binary revisions are costly.
Existing Docker builds CC-CEDICT offline from a small committed source; downloading
2.98 GB during every image build would lose that property and depend on a mutable
upstream URL. Deploying a separately verified file through the existing persistent
`./data:/app/data` mount avoids adding source downloads to runtime or image construction.
The application image itself remains built the same way.

Use the explicit, verified bundle installer described in
[distribution operations](dutch-dictionary-distribution.md). It installs SQLite,
manifest and attribution together under the existing persistent data mount.
Configure `.env` after installation:

```dotenv
READER_DUTCH_DICTIONARY=/app/data/dictionaries/current/dutch.sqlite3
```

Reader opens the resolved generation read-only at startup. Restart it explicitly
after installing/upgrading/rolling back. Runtime validates compatible schema,
builder and provenance metadata; compatible content updates no longer require an
application update. The installer verifies the exact independently pinned manifest
and all asset hashes before selection. No startup or Docker build downloads data.

If not configured, the default is `reader/dutch.sqlite3` adjacent to the module;
normal images do not include it and Dutch contextual behavior continues gracefully.
No environment path or SQLite contents are accepted from a Reader client.
